## Plain-English Summary

Autohop is in a strong overall state. The app has a clear product idea, a
download-first architecture, extensive AI-oriented source comments, a careful
CloudKit sync design, and modern SwiftUI navigation patterns. No hardcoded
secrets, analytics SDKs, or obvious unsafe logging paths were found in this pass.

A product-default correction was applied after the initial scan: automatic
downloads now clearly default to both Wi-Fi and cellular enabled. The code,
Settings copy, Support copy, `FEATURES.md`, website support copy, and regression
test now agree on that behavior.

The second major cleanup was language consistency. The visible page is now
consistently called **Up Next** in app copy, docs, onboarding copy, and website
copy. Internal names such as `QueueSheetView` and `downloadedQueue` are left in
place because renaming working implementation symbols would be high-churn and
low-value.

The main remaining improvement areas are architectural rather than emergency
bugs: `AppState` is very large, several UI files are also large, Release Radar and
download scheduling would benefit from more durable persisted work-intent
boundaries, and global app settings / per-podcast Download Filters do not yet
roam through iCloud Sync.

## Performance And Efficiency Findings

### P1 — Persist Auto-Download Intent Across Background Feed Refresh
**✅ RESOLVED 2026-07-04** — implemented as recommended (see backlog table for the
shape of the fix). Verification note from the fix pass: the impact was worse than
described below — after a *successful* BG refresh the feed is not "due" again
until its next release window, so a lost intent delayed the download until the
next app open, not merely the next wake.

Current behavior: feed refresh completes after fetching/parsing/merging the RSS
feed and schedules automatic media downloads separately. This is good for not
holding manual/timed refresh UI hostage to slow media transfers.

Risk: during a short `BGAppRefreshTask`, iOS can suspend the app soon after the
feed task finishes. If the media download task is only scheduled in an async
follow-up, there is a narrow timing window where a new episode is known but the
background URLSession transfer may not have been fully started.

Recommendation: persist a small "download intent" record when a feed merge finds
an eligible latest episode. Let foreground, background-audio, BGProcessing, and
download-manager resume code drain that intent idempotently. This makes Release
Radar and episode downloads more robust under short wakes.

### P2 — Split `AppState` By Domain
**⏳ STAGED — first carve done 2026-07-04.** Playback-position persistence
(~180 lines: file + write-through cache + subscription-scoped keys + resume
normalization + legacy decode) extracted to
`Persistence/PlaybackPositionStore.swift` — now in AutohopCore, compile-verified
and headless-tested (`Tests/PlaybackPositionStoreTests.swift`); AppState keeps
same-named thin wrappers so playback call sites are unchanged. Download-intent
persistence was likewise extracted earlier the same day (AH-01,
`AutoDownloadIntentStore`). The remaining large domains (feed-scheduling
orchestration, onboarding milestones, settings side effects) are deliberately
deferred to the tvOS proposal's Phase 0 cross-platform AppState/AutohopCore
refactor, which stages them with app-target compile checkpoints — do NOT bulk-
split the remaining 4.5k lines without building the app target between carves.

`AppState.swift` is 4,720 lines and coordinates playback, downloads, feeds, sync,
onboarding, sleep, stats, network gating, and UI-derived state. The file is well
commented, but it is still the largest risk surface for accidental regressions.

Recommendation: carve out actors/services for feed scheduling, download intent,
onboarding milestones, and settings-derived side effects. Keep `AppState` as the
UI facade, not the owner of every workflow.

### P2 — Reduce Broad SwiftUI Invalidations
**✅ MATERIALLY RESOLVED for high-churn domains (verified 2026-07-04).** Of the
domains named below: playback tick → PlaybackClock (2026-07-02); stats period
data → memoized ListeningStatsStore summaries; download activity →
DownloadActivityStore + ≥1% progress coalescing; and the last per-second broad
publisher, `@Published downloadProgress` on AppState, is now the dedicated
`DownloadProgressModel` observable (2026-07-04) — only the four
progress-rendering surfaces observe it. Remaining publishes (upNext, feed
refresh status, messages/toasts) are event-frequency, not per-second. The full
@Observable migration stays a separate staged follow-up.

The project uses `ObservableObject` / `@Published` rather than Swift's newer
fine-grained Observation model. This is compatible with iOS 17, but broad
`AppState` publishes can invalidate large views such as Player, Stats, and
Subscriptions.

Recommendation: introduce small view models or observable slices for high-churn
domains: playback tick/progress, download activity, feed refresh status, stats
period data, and Up Next count/artwork flash.

### P2 — Dynamic Type And Fixed Font Audit

The app uses many fixed `.font(.system(size: ...))` values. This gives a precise
music-app feel, but it can reduce Dynamic Type friendliness and increase text-fit
risk in Settings/Support/Stats on large accessibility sizes.

Recommendation: keep deliberate fixed icon/control geometry, but migrate body
copy, settings labels, support text, and long status descriptions toward semantic
fonts or explicit `@ScaledMetric` constraints.

### P3 — Website Generated Worker Is Large

`worker.js` embeds all static pages and large base64 app icons. This is acceptable
for a small Cloudflare-style worker, but every copy tweak regenerates a large diff.

Recommendation: when convenient, move repeated app icon imagery to a shared asset
URL or smaller inline thumbnail to reduce deploy diff noise.

## Background Refresh And Downloads

Strengths:

- BG task identifiers are registered for feed refresh and processing:
  `com.autohop.feedrefresh`, `com.autohop.feedprocessing`.
- Background modes include audio, fetch, processing, and remote-notification.
- BGAppRefreshTask is treated as a short opportunistic wake; BGProcessingTask is
  used for longer charging/network catch-up.
- Release Radar prioritization protects release-window candidates during limited
  background cycles: background cap 8, with 6 reserved slots for pre-window,
  active-window, and missed-release work.
- Conditional HTTP requests are documented and reduce feed-check cost when feeds
  return 304/not-modified.
- `DownloadManager` uses a background URLSession, validates status/MIME/tiny-body
  failures, supports pause/resume data, and excludes completed media from backup.
- Network gating is centralized through `NWPathMonitor` plus URL request cellular
  access.

Recommended improvements:

- Persist download intents as described above.
- Add a release-radar/background integration test around "new episode found during
  BGAppRefreshTask → URLSession task definitely started or intent persisted."
- Add metrics for `feed.autoDownloadScheduled` → `download.start` latency so real
  device logs can prove whether BG wakes are long enough.
- Consider draining a small bounded number of auto-download intents inside
  BGProcessingTask after feed catch-up.

## Security And Privacy Findings

No high-severity issue found.

Positive findings:

- No hardcoded API keys, tokens, or private secrets found in the local scan.
- Privacy manifest declares no tracking and no collected data types.
- Required API reasons are present for file timestamps and UserDefaults.
- Diagnostic log redaction exists and is tested.
- iCloud Sync is off by default and uses the user's private CloudKit database.
- Website privacy policy now matches shipped behavior more closely.

Reviewed tradeoffs:

- `NSAllowsArbitraryLoads = true` is enabled. This is a real App Transport
  Security relaxation, but the project comments justify it: podcast feeds, media,
  artwork, and user-entered RSS URLs can be arbitrary, and granular ATS media keys
  can interact badly with the broad need. Keep this documented for App Review.
- `aps-environment` and `remote-notification` exist because CloudKit sync may use
  Apple's silent push mechanism. Do not claim "Autohop never uses APNs" without
  qualifying that the developer does not run a push provider server.

Recommended improvements:

- Keep the privacy manifest synchronized with any future SDK, analytics, crash
  reporting, or networking addition.
- Add a short `SECURITY.md` describing supported disclosure path and the ATS
  rationale.
- Add one test that asserts log redaction covers feed URLs with query tokens and
  Authorization-like strings if not already covered for those exact shapes.
