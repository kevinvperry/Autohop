## 0. Plain-English summary (for a non-technical reader)

**Overall: the app is in very good shape.** It is carefully built, unusually well
documented, and defensively engineered. There are **no security problems**, **no
data-loss bugs**, and **no crashes** found in this scan. Most of the issues from the
last review have already been fixed. What remains is a short list of *refinements*,
not emergencies.

The three things most worth Kevin's attention:

1. **Text doesn't grow when the user makes their phone's text bigger.** iPhone has an
   accessibility setting that enlarges text everywhere. Autohop currently uses
   *fixed* text sizes in ~200 places, so people who rely on larger text (a sizeable
   share of users, and an Apple design expectation) won't see Autohop's text grow.
   This is the single biggest gap against modern Apple design standards. It's a
   polish/accessibility issue, not a bug — the app still works.

2. **One giant file is getting harder to maintain.** The "brain" of the app
   (`AppState.swift`) is now ~4,000 lines and has grown ~900 lines since the last
   review. It still works correctly, but very large files are slower to compile and
   riskier to change. Splitting it into smaller pieces would make future work safer
   and faster. (Recommendation only — nothing is broken.)

3. **A few release-checklist housekeeping items.** The app's version number in the
   build config still says "1.1" while the work is happening on a "1.2" branch, and
   the push-notification setting is in "development" mode (Apple normally flips this
   automatically when you submit, but it's worth confirming). These are the kind of
   things to tick off right before submitting an update.

The background features Kevin specifically asked about — **automatic feed checking
(Release Radar) and automatic episode downloads** — are genuinely well-built. They
use Apple's recommended background mechanisms correctly, adapt to each show's
publishing schedule, recover from interruptions, and avoid wasting battery/data.
This scan found only minor edge-case notes there, not real problems.

Bottom line: ship-quality. Address Dynamic Type for the next accessibility-focused
update, keep an eye on the size of `AppState.swift`, and run the small release
checklist before the next submission.

## 2. Performance & efficiency

### S1-PERF — none found
No S1 performance defects. The prior write-amplification (P1), main-thread position
re-reads (P2), and downloaded-queue recompute (P3) are all resolved and verified in
`ASSESSMENT.md`.

### DS1 — `[S2]` `AppState.swift` is a 4,074-LOC `@MainActor` god object and is growing
**Anchor:** `App/AppState.swift` (whole file). 4,074 LOC, 136 methods, 17
`@Published` properties, 33 inline `Task{}` closures. Was **3,199 LOC** at the prior
review (2026-06-17) → **+875 LOC** in ~6 days.
**Evidence:** the single type owns playback orchestration, the download pipeline
(`downloadEpisode`/`drainDownloadQueue`/`reconcileOrphanedDownloads`), the entire
Release Radar engine (`performRefreshCycle`, `refreshCandidatesForCycle`,
`reconcileDeferredRefreshBacklog`, `applyDeferredRefreshBoost`, scheduling, logging
helpers), auto-archive, listening history, onboarding milestones, and CloudKit
materialisation — all in one `@MainActor` class.
**Impact:** (a) **compile time** — any one-character edit recompiles the whole 4k-LOC
type under `wholemodule` Release builds; (b) **change risk** — 17 `@Published`
fields + 33 task closures in one actor make state-mutation reasoning hard and raise
the chance of an accidental retain cycle or out-of-order mutation; (c) **review
cost** — the file no longer fits a single reviewer pass. None of this is a runtime
defect today; it is a maintainability/throughput tax that compounds.
**Remediation (no behaviour change):** extract cohesive responsibilities into
same-actor `extension`s in separate files first (cheapest, zero-risk), then into
collaborator types behind narrow protocols where state is separable:
`FeedRefreshCoordinator` (the entire `performRefreshCycle`/candidate/backlog
cluster, ~600 LOC), `DownloadCoordinator` (`downloadEpisode`/`drainDownloadQueue`/
`reconcileOrphanedDownloads`/superseded-cleanup), and the refresh **logging
helpers** (`refreshDecisionMetadata`/`refreshStateCounts`/`refreshTopCandidateSummary`/
`refreshLogDate`/`refreshFeedHash`, all pure formatting) into a `RefreshLogFormatter`.
The Release Radar math is already correctly externalised into pure value types
(`FeedRefreshScheduling`, `FeedRefreshBudgeting`, `FeedRefreshPrioritizer`) — extend
that pattern to the orchestration shell.

### DS2 — `[S3]` `refreshDownloadedActivities()` rebuilds the full downloaded set on every completion
**Anchor:** `App/AppState.swift:1591` `refreshDownloadedActivities()`.
**Evidence:** `downloadedActivities = subscriptionStore.subscriptions.flatMap { $0.episodes.compactMap … }.sorted …` — an O(total-episodes) flat-map + allocate + sort over **every** episode of **every** subscription, run on each download completion, each superseded-cleanup, and each reconcile.
**Impact:** trivial for small libraries; for a large download-first library (many subs × ~50 episodes) this is a full re-scan + re-sort per completion during a catch-up burst. Main-actor work, but bounded and infrequent enough to be S3.
**Remediation (optional):** maintain `downloadedActivities` incrementally — insert/remove the single changed episode rather than rebuilding — or memoize behind the same invalidation hook already used for `cachedDownloadedQueue` (`invalidateDownloadedQueueCache`, `App/AppState.swift:263`).

### Confirmed-OK (credit, not findings)
- `downloadedQueue` is memoized (`cachedDownloadedQueue`, invalidated on store change) — P3 resolved.
- Saved playback positions are an in-memory write-through cache — P2 resolved.
- `AppLogger` holds one append handle for the queue lifetime — P4 resolved.
- GRDB episode rows are diffed, not rewritten wholesale — P1 resolved.

## 3. Background refresh (Release Radar) & episode downloads

> **Verdict: this subsystem is the strongest part of the codebase.** Apple's
> mechanisms are used correctly and the adaptive logic is genuinely sophisticated.
> Findings here are edge-case notes, not defects.

**Architecture confirmed correct:**
- Single `BGAppRefreshTask` (`com.autohop.feedrefresh`) registered before
  `didFinishLaunching` returns (`AppDelegate.swift:30`); identifier matches
  `Info.plist BGTaskSchedulerPermittedIdentifiers` and `BackgroundTaskCoordinator`.
- "No feeds due" reports `setTaskCompleted(success: true)` — correct; reporting
  failure would teach iOS to deprioritise wakes (`AppDelegate.swift:90-104`).
- Expiration handler cancels the active cycle and **checkpoints** unfinished
  selected feeds into a deferred backlog with age/count score-boosting so they win
  the next wake (`AppState.swift:2482`, `restoreUnfinishedRefreshBacklog:2970`,
  `applyDeferredRefreshBoost:2923`).
- Conditional GET fast-path: ETag/Last-Modified validators → a `304` returns
  `.notModified` with **zero parse cost** (`FeedService.swift:91-123`).
- Background downloads use a **background `URLSession`** that survives suspension;
  app-relaunch completions route through `onBackgroundDownloadCompleted` (no live
  continuation) and `handleEventsForBackgroundURLSession` (`DownloadManager.swift:457`,
  `AppDelegate.swift:59`). HTTP-status / MIME / implausibly-small-body gates prevent
  captive-portal/error pages from being stored as media (`DownloadManager.swift:471-527`).
- A 10-minute stall watchdog cancels with resume-data and schedules a retry; the
  recent commit (`8f33efd`) hardened it against re-queuing repeated checks during a
  stall (`DownloadManager.swift:723-767`).
- Background wakes **protect** Release-Radar / daily-release candidates via a
  reserved-slot budget so backlog work can't starve the latest-episode check
  (`refreshSubscriptionsForBackground` → `protectedStates`/`minimumProtectedSelections`,
  `AppState.swift:2470`).

### BG1 — `[S3]` ✅ RESOLVED (2026-06-23) — `isDownloadAllowed()` returned `true` when the network path is not yet known
**Resolution:** the unknown-path branch now returns `settings.downloadOverWifi` instead of an unconditional `true`, so a user who has disabled Wi-Fi downloads can't have one slip through the pre-`NWPathMonitor` window; default users (Wi-Fi on) are unaffected and cellular remains hard-gated at the transport layer (`URLRequest.allowsCellularAccess`). Original finding below.
**Anchor:** `App/AppState.swift:560`.
**Evidence:**
```swift
guard let path = latestNetworkPath, path.status == .satisfied else { return true }
if path.usesInterfaceType(.wifi)     && !settings.downloadOverWifi     { return false }
if path.usesInterfaceType(.cellular) && !settings.downloadOverCellular { return false }
return true
```
`latestNetworkPath` is populated asynchronously by `NWPathMonitor` (`startNetworkMonitor:553`). In the window between launch and the first path callback, `latestNetworkPath == nil` → the function returns `true`, bypassing the **Wi-Fi** toggle.
**Impact:** low. Cellular is **independently** gated at the transport layer
(`request.allowsCellularAccess = allowsCellular`, `DownloadManager.swift:189`), so a
cellular download cannot start even if this returns `true`. The only bypassable case
is the unusual `downloadOverWifi = false` user, and only for the brief pre-monitor
window. No data risk.
**Remediation (optional):** when `latestNetworkPath == nil`, either defer the
auto-download decision until the first path update, or fail-closed for the explicit
`downloadOverWifi == false` case. Document the chosen default in the header.

### BG2 — `[S3]` Auto-download kicked off after a *background* refresh is fire-and-forget, outside the BGTask keep-alive
**Anchor:** `App/AppState.swift:2357` `scheduleAutoDownloadAfterRefresh` wraps
`runAutoDownloadAfterRefresh` in a detached `Task { @MainActor … }` that
`performRefreshCycle` does **not** await; the `BGAppRefreshTask` reports completion
as soon as `refreshSubscriptionsForBackground()` returns (`AppDelegate.swift:96`).
**Evidence:** the refresh cycle returns after the feed merge; the auto-download Task
runs independently. If the system suspends the app immediately after
`setTaskCompleted`, the main-actor work that calls `downloadManager.download(...)` →
`task.resume()` may not execute until the next foreground/relaunch.
**Impact:** low and **non-destructive** — the auto-download is not lost; it resumes
when the app is next scheduled/foregrounded. Worst case is added latency before the
newest episode begins downloading after a background-only wake. Once `task.resume()`
*has* run, the background `URLSession` owns the transfer and suspension is safe.
**Remediation (optional, only if background-download latency is observed):** start
the `download()` task **within** the refresh cycle's awaited window (so `resume()`
is reached before `setTaskCompleted`), or request a short `beginBackgroundTask`
assertion around the enqueue so `resume()` is guaranteed to run.

### BG3 — `[S3]` Background wake budget is fixed; no `BGProcessingTask` for large catch-up
**Anchor:** `AppState.refreshSubscriptionsForBackground` uses
`backgroundRefreshFeedLimit`; only `BGAppRefreshTask` is registered (Info.plist
declares `fetch`, deliberately **not** `processing`, `project.yml:128-131`).
**Evidence/assessment:** this is a **correct, conservative** choice — `BGAppRefreshTask`
wakes are short (~30 s) and the reserved-slot + deferred-backlog design already
handles "more feeds due than slots." Adding a `BGProcessingTask` (longer, charger/Wi-Fi
gated) *could* let a large library fully catch up overnight, but it adds a second
scheduler surface and an App-Review justification. **Not recommended now** — noted
only as the known scaling lever if very-large-library users report stale feeds.

## 7. Apple modern design compliance

> **Modern APIs are well adopted** — `NavigationStack` everywhere, iOS-17
> two-parameter `.onChange`, `.foregroundStyle` (378×) having nearly replaced
> `.foregroundColor` (2×). The **one systemic gap** is Dynamic Type.

### UI1 — `[S2]` Dynamic Type is effectively unsupported (fixed font point sizes throughout)
**Anchor:** 206 occurrences of `.font(.system(size: N …))` across `Views/`; only
~1 file (`Views/EpisodeBadges.swift`) uses a Dynamic-Type-aware path (`relativeTo:`),
and **zero** views use `ScaledMetric` or read `dynamicTypeSize`/`@Environment(\.sizeCategory)`.
**Evidence (text, not icons):**
```
Views/PodcastsView.swift:63          .font(.system(size: 13, weight: .semibold))
Views/PodcastsView.swift:196         .font(.system(size: 22, weight: .bold, design: .rounded))
Views/GettingStartedChecklist.swift:74 .font(.system(size: 17, weight: .semibold))
Views/PodcastDetailView.swift:340    .font(.system(size: 30, weight: .semibold))
Views/StarterPacksView.swift:153     .font(.system(size: 17, weight: .bold))
```
These are applied to **labels and titles**, not just SF Symbols. Deployment target
is iOS 17 (`project.yml:34`), so the full semantic-font + `relativeTo:` toolkit is
available.
**Impact:** users who raise the system text size (Settings → Accessibility → Display
& Text Size → Larger Text, and the standard Dynamic Type slider) will see **no
change** in Autohop's text. This is the clearest deviation from Apple's Human
Interface Guidelines ("support Dynamic Type") and is the kind of thing flagged by an
accessibility audit. It is usability/accessibility, not a crash.
**Remediation (incremental, no behaviour change for default text size):**
- Prefer semantic styles (`.font(.headline)`, `.subheadline`, `.body`, `.caption`)
  wherever a fixed size maps cleanly to one.
- Where a specific size is genuinely needed, use the relative form
  `.font(.system(size: 17, weight: .semibold, design: .rounded), relativeTo: .body)`
  (iOS 17+) or wrap dimensions in `@ScaledMetric`.
- Leave **SF Symbol-only** sizes alone where they're paired with a symbol that
  should not grow (verify case-by-case).
- Adopt incrementally — start with the primary reading surfaces (episode lists,
  Podcast Detail, Player metadata) and gate at `accessibility1`/`accessibility3` to
  confirm layouts don't break, optionally clamping with `.dynamicTypeSize(...up to:)`.

### UI2 — `[S3]` ✅ ADDRESSED (2026-06-23) — Sparse explicit accessibility coverage outside core controls
**Resolution:** the systemic gap was 11 identical icon-only toolbar back buttons
(`Button { dismiss() } label: { Image(systemName: "chevron.left.circle.fill") }`,
raw `Image`, no label) across DownloadsView, DiscoverView, SettingsView,
SubscriptionSettingsView (×2), PodcastDetailView, AddFeedView, DiagnosticLogView,
SleepScheduleView, AcknowledgementsView, TopEpisodesView — each now carries
`.accessibilityLabel("Back")`. The remaining icon controls were verified
already-accessible (SwiftUI `Label` keeps its title under `.labelStyle(.iconOnly)`;
other icon+text rows read their adjacent `Text`). Original finding below.
**Anchor:** 7 of 34 `Views/*.swift` files use any `accessibility*` modifier.
**Evidence/nuance:** the **most critical** surface is already well-covered — the
Player transports carry explicit labels (`PlayerView.swift:810` Play/Pause,

video). SwiftUI also auto-derives labels from visible text, so text-labelled buttons
are not silent. The gap is **icon-only controls and composed rows** in secondary

**Impact:** moderate; localized to non-player surfaces.
**Remediation:** a VoiceOver pass over Downloads, Discover, Stats, and the episode

button and `accessibilityElement(children: .combine)` to multi-`Text` rows that
should read as one element.

### UI3 — `[—]` ❌ WITHDRAWN — false positive on call-site inspection (2026-06-23)
The four sites a raw grep flagged as deprecated SwiftUI modifiers are **not**
deprecated, and "modernising" them would break compilation or behaviour. Left
unchanged intentionally:
- `Views/StatsView.swift:372` and `:779` — `.cornerRadius(3)` is chained on a Swift
  Charts **`BarMark`** inside a `Chart { … }` closure. That is
  `ChartContent.cornerRadius(_:style:)` (the correct way to round bar corners), **not**
  the soft-deprecated SwiftUI `View.cornerRadius`. `.clipShape` is not a `ChartContent`
  modifier and would not compile here.
- `Views/PodcastDetailView.swift:374,377` — `.foregroundColor` is applied to `Text`
  values **concatenated with `+`**
  (`Text(desc).foregroundColor(.secondary) + Text("…less").foregroundColor(.purple)`).
  `Text.foregroundColor(_:) -> Text` is the required idiom for coloured runs in a `Text`
  concatenation; `foregroundStyle` returns `some View` and cannot participate in `Text + Text`.
**Action:** none. (Caught by reading each call site in context before editing — the
raw count in §1 is accurate, but every instance is legitimate.)

## 8. Architectural strengths to preserve

- **Adaptive Release Radar:** learned publish-cadence profiles, conditional GETs,
  priority budgeting with protected slots, and an age/count-boosted deferred backlog
  that survives background-wake expiry. Release Radar math is isolated in pure,
  headlessly-tested value types — keep that boundary.
- **Resilient download layer:** background `URLSession`, resume-data on pause/stall,
  zombie/duplicate guards keyed by both episodeID and media URL, multi-gate
  integrity validation, and app-relaunch completion handling.
- **Single-writer persistence** with snapshot-diffed, coalesced, atomic writes and
  episode-level row diffing.
- **Two-path playback** (AVPlayer / AVAudioEngine) with render watchdog, EOF
  sentinel, and the recently-hardened AirPods route-change handling.
- **Documentation discipline:** every non-test source carries an `AI CONTEXT`
  header; this is what made a fast, accurate scan possible. Keep them current.
