## 0. Plain-English summary (for a non-technical reader)

**Overall: the app remains in very good, ship-quality shape.** The scan found **no
security problems, no data-loss bugs, and no crashes.** The download and background
systems Kevin specifically asked about are genuinely well-engineered and have
*improved* since the last review (a longer overnight "catch-up" task and refresh-
during-listening were both added and are working). What remains is a short list of
*refinements*, plus two newly-surfaced efficiency opportunities. Nothing here is an
emergency.

The five things most worth attention, in order:

1. **The app does more work than it needs to while you listen (battery).** Twice a
   second during playback, the app tells *every screen currently on display* "I
   changed — redraw if needed," even screens that don't show the playback time.
   Separately, every 30 seconds it re-calculates the publishing schedule for *every*
   podcast from scratch. Both are invisible (the app stays smooth), but they burn a
   little extra battery during exactly the moments the app is trying to be frugal.
   Both have clean, well-understood fixes using a newer Apple technology (the
   "Observation" framework, available since iOS 17).

2. **Bigger text still doesn't work (accessibility).** iPhone lets users enlarge
   text everywhere via an accessibility setting. Autohop still uses *fixed* text
   sizes in ~210 places, so people who rely on larger text won't see Autohop's text
   grow. This is the single clearest gap against Apple's design standards. It's a
   polish/accessibility issue, not a bug — and it's slightly *worse* than last time
   (the one screen that used to scale no longer does).

3. **A new-episode download found in the background might not start until you next
   open the app.** When the app wakes briefly in the background, finds a new
   episode, and tries to start its download, the start can be cut off when iOS
   suspends the app again. Nothing is lost — the download begins when the app next
   wakes or you open it — but it can be delayed. There's a known, small fix.

4. **The "brain" file keeps growing.** The central file (`AppState.swift`) is now
   ~4,600 lines (up ~550 since last review). It still works correctly, but very
   large files are slower to compile and riskier to change. Splitting it would make
   future work safer. (Recommendation only — nothing is broken.)

5. **Two release-checklist items.** The build's version number still says "1.1"
   while work happens on a "1.2" branch (Kevin has chosen to set this at release
   time), and the push-notification setting is in "development" mode (Apple normally
   flips this automatically at submission — worth confirming on the final build).

Bottom line: ship-quality. The biggest *new* value is in item 1 (two efficiency
wins in the battery-sensitive listening window). Items 2–5 are known refinements.

## 2. Performance & efficiency

### PERF-1 — `[S2]` `ObservableObject` fires a global invalidation ~2×/s during playback (legacy observation pattern)
**Anchor:** `App/AppState.swift:136` `final class AppState: ObservableObject`;
`:157` `@Published var currentPlayerTime`; written every 0.5 s at `:766`
(`state.currentPlayerTime = time` inside `playbackEngine.onTimeUpdate`). 24 view
files observe `AppState` via `@EnvironmentObject` (e.g. `RootView.swift:68`,
`PodcastsView.swift:28`, `StatsView.swift:38`, `QueueSheetView.swift:30`,
`PlayerView.swift:47`).
**Evidence:** `currentPlayerTime` is `@Published`. With `ObservableObject`, **any**
`@Published` mutation fires `objectWillChange`, and SwiftUI re-evaluates the `body`
of **every on-screen view** that holds a reference to that object — there is no
per-property dependency tracking. The scrubber legitimately needs a 2 Hz update, but
the same publish also invalidates unrelated on-screen surfaces (a visible
`StatsView` with Swift Charts, a long `PodcastsView`/`QueueSheetView` list, the
mini-player overlaid on any tab) twice per second for the entire duration of
playback.
**Impact:** continuous, avoidable `body` re-evaluation (and any computed-property
work inside those bodies) at 2 Hz during playback — the battery-sensitive window the
background-audio design is otherwise careful to economize. SwiftUI's structural
diffing prevents most *redraws*, but body re-evaluation still runs; cost concentrates
on heavy bodies (charts, large lazy stacks). Not a correctness bug; a steady energy/CPU
tax proportional to on-screen body complexity.
**Remediation (two options, low risk):**
- **Targeted (cheapest):** move the 2 Hz value out of `AppState` into a tiny
  dedicated `ObservableObject` (e.g. `PlaybackClock { @Published var time }`) that
  *only* the scrubber and Now-Playing surfaces observe. The 24 `AppState` observers
  then no longer wake on every tick.
- **Strategic (also closes the modernity gap, see UI3):** migrate `AppState` (and
  peer stores) to the iOS-17 **Observation framework** (`@Observable` +
  `@Environment`/`@State`, dropping `@Published`/`ObservableObject`/`@EnvironmentObject`).
  `@Observable` tracks which properties each `body` actually reads, so a
  `currentPlayerTime` change re-evaluates **only** views that read it. Deployment
  target is iOS 17 (`project.yml:34`), so the API is fully available. Mechanical but
  broad; stage it (leaf views first), and consider doing PERF-1 + UI3 together.

### PERF-2 — `[S2]` Release-Radar schedule profiles are recomputed from scratch for every feed every 30 s (no memoization)
**Anchor:** poll loop `App/AppState.swift:4278` `startForegroundPolling()` →
`:4287` `subscriptionStore.subscriptions.filter { … nextRefreshDue(for:) <= now }`
→ `nextRefreshDue` (`:3054`) → `refreshPrediction` (`:3130/:3142`) →
`releaseRadarProfile` (`:3138`) → `subscription.refreshStats.scheduleProfile(...)`
(`Models/Subscription.swift:412`) → `FeedScheduleProfiler.profile(from: …)`.
**Evidence:** `scheduleProfile` is a **pure computed function** with no cache:
```swift
public func scheduleProfile(downloadFilterSettings:…, calendar:…) -> FeedScheduleProfile {
    FeedScheduleProfiler.profile(from: releaseObservations(includedBy: downloadFilterSettings), calendar: calendar)
}
```
The profiler runs the full v2 detector pipeline (hourly → rolling-bulletin → burst →
`regularCadenceProfile`), each stage doing `sorted`/`map`/`filter`/`zip`/clustering
over up to `maxReleaseObservations = 200` observations (`Subscription.swift:281`).
The foreground/background-audio poll fires **every 30 s** while `isAppForeground ||
isPlaying` and computes this for **every** subscription just to count how many are
due; each `refreshDueSubscriptions()` cycle then recomputes again via
`refreshCandidatesForCycle`. For a 71-feed library that is ~71 full profile builds
(≈ up to 200 obs each, multiple passes) every 30 s during listening, plus the
diagnostics screens that call the same path.
**Impact:** repeated, fully-cacheable CPU in the battery-sensitive background-audio
window. Scales with `library_size × observation_cap`. Invisible on small libraries;
measurable energy cost on large ones (Kevin's own test library is ~71 feeds).
**Remediation:** memoize `FeedScheduleProfile` per subscription. The profile is a
pure function of `releaseObservations` + `downloadFilterSettings`, which change
**only** when a feed is refreshed (new observations recorded) or filter settings
edited. Cache keyed by subscription ID with an invalidation hook on
`updateRefreshStats`/`updateEpisodes`/filter changes (mirrors the existing
`cachedDownloadedQueue` / `invalidateDownloadedQueueCache` pattern at
`AppState.swift:263`). Alternatively store a lightweight `nextDueAt` alongside
`refreshStats` and recompute only on change.

### PERF-3 — `[S3]` `refreshDownloadedActivities()` rebuilds the entire downloaded set on every change (carryover DS2, unchanged)
**Anchor:** `App/AppState.swift:1798`.
**Evidence:** `downloadedActivities = subscriptionStore.subscriptions.flatMap { $0.episodes.compactMap … }.sorted …`
— an O(total-episodes) flat-map + allocate + sort over **every** episode of **every**
subscription, run on each download completion, superseded-cleanup, and reconcile.
**Impact:** trivial for small libraries; a full re-scan + re-sort per completion
during a catch-up burst for large download-first libraries. Bounded, main-actor, S3.
**Remediation:** maintain `downloadedActivities` incrementally (insert/remove the one
changed episode) or memoize behind the same invalidation hook as
`cachedDownloadedQueue`.

### PERF-4 — `[S3]` Per-tick playback diagnostics run on every 0.5 s tick
**Anchor:** `App/AppState.swift:758` (`measure(_:_:)` closure), `:824`
`recordPlaybackTickDiagnostics`, impl `:3773`.
**Evidence:** every 0.5 s tick allocates a `[PlaybackTickStageTiming]`, runs 6
`measure` closures each calling `CFAbsoluteTimeGetCurrent()` twice, then builds a
`PlaybackTickDiagnostics` value, computes `stages.max{…}`, and updates a rolling
summary. `lastPlaybackTickDiagnostics` is a **plain** `private var` (not `@Published`,
`:265`) so it does not itself trigger UI invalidation — good.
**Impact:** small, bounded instrumentation overhead in the hot path (~2 Hz). Useful
for the diagnostics screens; not a defect. Noted for completeness.
**Remediation (optional):** gate the fine-grained `measure`/stage-timing capture
behind `AppLogger.shared.isEnabled` (diagnostic logging toggle) so production playback
skips the allocation when diagnostics are off; keep the cheap slow-tick warning.

### PERF-5 — `[S3]` Feed refresh within a cycle is fully serial (no bounded concurrency)
**Anchor:** `App/AppState.swift:2980` `for (index, subscription) in subscriptions.enumerated() { … await refreshSubscription(...) }`.
**Evidence:** each feed is fetched/parsed/merged one at a time. For a `BGAppRefreshTask`
(short, capped) this is correct and conservative. For **manual pull-to-refresh of the
whole library** and the **uncapped `BGProcessingTask` overnight sweep**
(`refreshSubscriptionsForProcessing`, `maxSubscriptions: nil`, `:2741`), serial
fetching maximizes wall-clock time.
**Impact:** longer manual "refresh all" and longer overnight catch-up than necessary;
no correctness issue. Serial keeps peak memory and connection count low (a deliberate,
defensible tradeoff).
**Remediation (optional):** for the manual and processing paths only, use a
`TaskGroup` with a small concurrency limit (e.g. 3–4 in-flight) and per-feed
cancellation checks. Leave the short `BGAppRefreshTask` path serial. Verify against
peak-memory budget on device before adopting.

### DS-GOD — `[S2]` `AppState.swift` is a 4,624-LOC `@MainActor` god object and is still growing (carryover DS1)
**Anchor:** `App/AppState.swift` (whole file). 4,624 LOC (was 3,199 at 2026-06-17,
4,074 at 2026-06-23 → **+550 in ~3 days**), 17 `@Published`, 33 inline `Task{}`.
**Evidence:** one `@MainActor` class owns playback orchestration, the download
pipeline, the entire Release Radar engine (refresh cycle, candidate selection,
deferred backlog, scheduling, formatting helpers), auto-archive, listening history,
onboarding milestones, and CloudKit materialisation.
**Impact:** (a) compile time — a one-character edit recompiles the whole 4.6k-LOC
type under `wholemodule` Release builds; (b) change risk; (c) review cost (no longer
fits one reviewer pass). No runtime defect; a maintainability tax that compounds.
**Remediation (no behaviour change):** extract cohesive responsibilities into
same-actor `extension`s in separate files first (zero-risk), then collaborator types:
`FeedRefreshCoordinator` (refresh cycle + candidate/backlog cluster),
`DownloadCoordinator` (`downloadEpisode`/`drainDownloadQueue`/`reconcileOrphanedDownloads`),
and a `RefreshLogFormatter` for the pure log-formatting helpers. The Release Radar
*math* is already correctly isolated into pure value types (`FeedScheduleProfiler`,
`FeedRefreshScheduling/Budgeting/Prioritizer`) — extend that pattern to the
orchestration shell. **Doing PERF-1's `@Observable` migration is a natural moment to
also split this file.**

## 3. Background refresh (Release Radar) & episode downloads

> **Verdict: still the strongest part of the codebase, and stronger than last pass.**
> The `BGProcessingTask` overnight catch-up and the refresh-during-background-audio
> poller are both now present and correctly wired. Findings below are edge-case notes.

**Architecture confirmed correct (re-verified on current HEAD):**
- **Two** background tasks registered before `didFinishLaunching` returns:
  `com.autohop.feedrefresh` (`BGAppRefreshTask`, ~30 s) and
  `com.autohop.feedprocessing` (`BGProcessingTask`, charging+Wi-Fi catch-up) —
  `AppDelegate.swift:82-109`. Both identifiers appear in
  `Info.plist BGTaskSchedulerPermittedIdentifiers` (`Info.plist:5-9`) and
  `BackgroundTaskCoordinator` (`:24-25`). `UIBackgroundModes` declares exactly
  `audio, fetch, processing, remote-notification` (`Info.plist:56-62`), each with a
  handler — matches App Review guideline 2.5.4.
- Each handler **reschedules the next request first** (`AppDelegate.swift:115,144`),
  runs `Task { await … }`, reports `setTaskCompleted(success: true)` even for
  "nothing due", and on expiration calls `cancelRefreshCycleIfBackgroundOnly` +
  `work.cancel()`.
- `cancelRefreshCycleIfBackgroundOnly` (`AppState.swift:2768`) only aborts when **no**
  live foreground/audio context owns the cycle (uses real `isAppForeground || isPlaying`,
  not the cacheable `isSceneActive`) — so an expiring BGTask that merely *joined* a
  live cycle **detaches** instead of killing shared work. A genuine cancel checkpoints
  unfinished selected feeds into the age/count-boosted deferred backlog
  (`restoreUnfinishedRefreshBacklog`, `performRefreshCycle:3010-3032`).
- `BGProcessingTask` is gated `requiresExternalPower = true` + `requiresNetworkConnectivity = true`,
  no `earliestBeginDate` (lets iOS pick the charging-idle window) — `BackgroundTaskCoordinator.swift:90-110`.
  Both `…IfNeeded` submitters guard on `getPendingTaskRequests` so launches don't reset the clock.
- Conditional GET fast-path: ETag/Last-Modified → a `304` returns `.notModified` with
  **zero parse cost** (`FeedService.swift`, `refreshIfModified`).
- Background downloads use a background `URLSession` (`isDiscretionary = false`,
  `sessionSendsLaunchEvents = true`, `DownloadManager.swift:96-103`); app-relaunch
  completions route through `onBackgroundDownloadCompleted` (no live continuation) and
  `handleEventsForBackgroundURLSession` (`AppDelegate.swift:66-78`). Multi-gate
  integrity validation (HTTP status / MIME / implausibly-small body) prevents
  captive-portal/error pages from being stored as media (`DownloadManager.swift:470-529`,
  `673-708`). Files stored under UUID names — no server-controlled path traversal.
- 10-minute stall watchdog cancels with resume data and fires `onWatchdogCancelled`
  for retry (`DownloadManager.swift:725-769`); the watchdog deliberately does **not**
  pre-clear task tracking (would orphan the retry callback).
- Background wakes **protect** Release-Radar / daily-release candidates via a
  reserved-slot budget (`refreshSubscriptionsForBackground` → `protectedStates` /
  `minimumProtectedSelections`, `AppState.swift:2711-2732`).
- BG1 (prior pass) **re-verified resolved**: `isDownloadAllowed()` returns
  `settings.downloadOverWifi` (not unconditional `true`) when the network path is not
  yet known; cellular remains hard-gated by `URLRequest.allowsCellularAccess`
  (`AppState.swift:710-725`, `DownloadManager.swift:190`).

### BG-1 — `[S3]` Auto-download after a *background* refresh is fire-and-forget, outside the BGTask keep-alive window (carryover BG2, still open — elevated given focus)
**Anchor:** `App/AppState.swift:2494` `scheduleAutoDownloadAfterRefresh(...)` (called
inside `refreshSubscription`), impl `:2586` wraps `runAutoDownloadAfterRefresh` in a
detached `Task { @MainActor [weak self] … }` that `refreshSubscription` /
`performRefreshCycle` do **not** await. The `BGAppRefreshTask` reports
`setTaskCompleted(success: true)` as soon as `refreshSubscriptionsForBackground()`
returns (`AppDelegate.swift:118-125`).
**Evidence:** the refresh cycle returns after the feed merge; the auto-download Task
runs independently. If iOS suspends the app right after `setTaskCompleted`, the
main-actor work that reaches `downloadManager.download(...) → task.resume()` may not
execute until the next foreground/relaunch.
**Impact:** low and **non-destructive** — the download is not lost; it begins when the
app is next scheduled/foregrounded. Worst case is added latency before the newest
episode starts downloading after a *background-only* wake. Once `task.resume()` has run,
the background `URLSession` owns the transfer and suspension is safe. This is the single
most actionable item under the user's explicit "Episode Downloads in background" focus.
**Remediation:** make the auto-download enqueue reachable **inside** the awaited BGTask
window so `task.resume()` is hit before `setTaskCompleted`. Either (a) `await` the
auto-download enqueue within `performRefreshCycle` (start the transfer, do not await
its *completion* — the background session finishes it after suspension), or (b) wrap
the enqueue in a short `UIApplication.beginBackgroundTask` assertion so `resume()` is
guaranteed to run. Keep the current detached behaviour for the foreground/processing
paths where it is already fine.

### BG-2 — `[S3]` Both BGTask handlers can double-call `setTaskCompleted` (no `hasCompleted` guard)
**Anchor:** `App/AppDelegate.swift:117-137` (refresh) and `:146-164` (processing).
**Evidence:** the `work` Task calls `task.setTaskCompleted(success: true)`; the
`expirationHandler` calls `task.setTaskCompleted(success: false)`. A late expiration
firing after the work already completed would double-call.
**Impact:** negligible — iOS tolerates a redundant `setTaskCompleted`. Cosmetic
robustness only.
**Remediation (tidy):** a single `hasCompleted` flag (or `os_unfair_lock`/actor-isolated
bool) checked in both paths so exactly one completion is reported.

### BG-3 — `[S3]` Changed-feed body size is not code-enforced against the ~100 KB budget
**Anchor:** `Feeds/FeedService.swift` (`refresh`/`refreshIfModified`); response parsed
without a byte cap. Episodes are capped by **count** (`defaultFeedEpisodeLimit`/50),
not by bytes.
**Evidence:** conditional GET makes an **unchanged** feed ≈ 0 bytes (`304`). A
**changed** feed returns a full body; Apple's ~100 KB-per-refresh guideline is
*helped* (count cap) but not *enforced*.
**Impact:** low. Most podcast feeds are well under budget; the count cap bounds parse
cost. Only pathologically large feeds could exceed the soft guideline, risking iOS
deprioritising future wakes.
**Remediation (optional):** cap the download with a streaming byte limit (e.g. abort
> ~512 KB) or honour `expectedContentLength` before reading the body; log when a feed
exceeds the soft budget so outliers are visible in diagnostics.

### BG-4 — `[note]` `BGProcessingTask` is now declared & justified — confirm App Review notes ship with it
**Anchor:** `Info.plist:61` (`processing` mode), `:8` (`com.autohop.feedprocessing`);
justification in `APPSTORE_ROADMAP.md` (Review Notes appendix per
`BACKGROUND_REFRESH_RESEARCH.md` §7 Tier 2 #3).
**Assessment:** correct and well-documented. **No change needed** — listed so the next
submission's review notes are confirmed to include the processing-mode justification
(adding a second BGTask surface is the kind of thing App Review queries).

## 7. Apple modern-design compliance

> **Modern APIs are well adopted** — `NavigationStack` everywhere (no `NavigationView`),
> iOS-17 two-parameter `.onChange`, `.foregroundStyle` over deprecated
> `.foregroundColor`, structured concurrency with 85 `@MainActor` annotations, and an
> explicit design-system discipline (`DESIGN.md`). Accessibility coverage **improved**
> (18/37 view files now use `accessibility*`, 41 `accessibilityLabel`). Two gaps remain.

### UI-1 — `[S2]` Dynamic Type is unsupported (fixed font point sizes throughout) — slightly regressed
**Anchor:** **210** occurrences of `.font(.system(size: N …))` across `Views/`; **zero**
views use `ScaledMetric`, `dynamicTypeSize`, `@Environment(\.sizeCategory)`, or the
`relativeTo:` semantic-scaling form. (The single prior `relativeTo:` site in
`EpisodeBadges.swift` is gone — it now uses two more fixed `system(size: 8)` badges at
`:67,:96` — so the count regressed to 0.)
**Evidence (text labels, not just icons):**
```
Views/PodcastsView.swift:196     .font(.system(size: 22, weight: .bold, design: .rounded))
Views/PodcastDetailView.swift    .font(.system(size: 30, weight: .semibold))
Views/GettingStartedChecklist.swift:74 .font(.system(size: 17, weight: .semibold))
```
Deployment target is iOS 17, so the full semantic-font + `relativeTo:` + `ScaledMetric`
toolkit is available.
**Impact:** users who raise the system text size (Settings → Accessibility → Display &
Text Size → Larger Text) see **no change** in Autohop's text. Clearest deviation from
Apple's HIG ("support Dynamic Type"); the kind of thing an accessibility audit flags.
Usability/accessibility, not a crash.
**Remediation (incremental, no change at default text size):**
- Prefer semantic styles (`.font(.headline/.subheadline/.body/.caption)`) where a fixed
  size maps cleanly.
- Where a specific size is needed, use `.font(.system(size: 17, weight: .semibold,
  design: .rounded), relativeTo: .body)` (iOS 17+) or wrap dimensions in `@ScaledMetric`.
- Leave SF-Symbol-only sizes paired with non-scaling glyphs alone (case-by-case).
- Start with primary reading surfaces (episode lists, Podcast Detail, Player metadata),
  test at `accessibility1`/`accessibility3`, and optionally clamp with
  `.dynamicTypeSize(…up to:)`.

### UI-2 — `[S3]` Deprecated `UIScreen.main` in new CarPlay artwork code
**Anchor:** `CarPlay/CarPlayArtworkProvider.swift:42` `scale: UIScreen.main.scale` and
`:49` `format.scale = UIScreen.main.scale`.
**Evidence:** `UIScreen.main` is deprecated (iOS 16+). In a CarPlay context it is also
semantically wrong — the car display is not the device's main screen, so its scale may
differ.
**Impact:** low — compiles with a deprecation warning today; artwork could render at the
wrong scale on the head unit. Will become a harder break in a future SDK.
**Remediation:** derive scale from the CarPlay scene's trait collection
(`traitCollection.displayScale`) or the connected `CPInterfaceController`/`CPWindow`'s
`traitCollection`, rather than `UIScreen.main`.

### UI-3 — `[S2, ties to PERF-1]` Observation framework (`@Observable`) not adopted
**Anchor:** 15 `ObservableObject` conformances, 0 `@Observable` (whole app).
**Evidence:** state is modelled with the pre-iOS-17 `ObservableObject` + `@Published` +
`@EnvironmentObject` pattern throughout. iOS 17's Observation framework (`@Observable`)
is Apple's current recommendation and provides per-property dependency tracking (the
direct fix for PERF-1's 2 Hz over-invalidation).
**Impact:** combined performance (PERF-1) + modernity gap. Not a defect.
**Remediation:** see PERF-1. Migrate leaf views/stores first; pair with the
`AppState.swift` split (DS-GOD).

### Confirmed-modern (credit)
`NavigationStack` (no `NavigationView`), iOS-17 `onChange(of:_:)` two-param form,
`.foregroundStyle` adoption (the 2 residual `.foregroundColor` + 2 `.cornerRadius`
sites are the legitimate concatenated-`Text` and Swift-Charts `BarMark` idioms — not
the deprecated SwiftUI modifiers; see prior pass §7 UI3 for the call-site proof),
`@UIApplicationDelegateAdaptor` bridge, `scene.windows` (modern, not
`UIApplication.shared.windows`) in `NativeVideoPlayerView.swift:42-43`, and structured
concurrency throughout.

## 8. Architectural strengths to preserve

- **Adaptive Release Radar v2:** identity-vs-scheduling split, recency-weighted
  per-weekday publish probabilities, densest-mode windows + soft tail, three-tier watch
  intensity — all isolated in pure, headlessly-tested value types
  (`FeedScheduleProfiler` in `Models/Subscription.swift`,
  `Tests/ReleaseRadarSchedulingTests.swift`). Keep this boundary; PERF-2 is about
  *caching* the output, not changing the math.
- **Two-tier background execution:** short `BGAppRefreshTask` + charging `BGProcessingTask`,
  plus the background-audio poller — the three windows iOS actually grants, used
  correctly, with reserved-slot budgeting and a checkpointed deferred backlog.
- **Resilient download layer:** background `URLSession`, resume-data on pause/stall,
  zombie/duplicate guards keyed by episodeID **and** media URL, multi-gate integrity
  validation, app-relaunch completion handling, backup-exclusion + locked-device file
  access for CarPlay.
- **Single-writer persistence** with snapshot-diffed, coalesced, atomic writes and
  episode-level row diffing.
- **Documentation discipline:** every non-test source carries an `AI CONTEXT` header;
  this is what made a fast, accurate scan possible. Keep them current.
